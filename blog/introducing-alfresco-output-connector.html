Enterprise ECM Replatforming & Zero-Trust Ingestion: Announcing the Alfresco Content Services Output Connector

Consolidating enterprise content from legacy silos—such as IBM FileNet P8, OpenText Documentum, Microsoft SharePoint, or network file systems—into a unified target repository like Alfresco Content Services (ACS) is one of the most critical challenges facing enterprise IT. Migrations cannot compromise: they require bit-for-bit binary fidelity, automatic recreation of hierarchical folder structures (cm:folder), synchronization of metadata properties and aspects, strict Zero-Trust Access Control List (ACL) replication, pre-flight authority validation against target directories, and automated audit reporting. Today, we are proud to introduce the brand new Alfresco Content Services Output Connector (oc-alfresco-output-connector) operating strictly in Migration Mode! 🚀

1. The Enterprise Replatforming Challenge

While OpenCrawling’s primary RAG mode parses documents via Apache Tika, splits them into semantic chunks, and calculates high-dimensional vector embeddings, content migration demands a completely different approach.

When enterprises migrate tens of millions of records into Alfresco Content Services:

  • Original Binaries Must Remain Pristine: CAD models, signed PDF contracts with cryptographic certificates, TIFF archives, and high-resolution media must be transferred bit-for-bit without alteration.
  • Hierarchies Must Be Maintained: Source folder trees must be seamlessly translated into Alfresco cm:folder nodes without duplicating intermediate folders or causing race conditions.
  • Security & Permissions Must Be Preserved: Access control rules from the source must be translated into Alfresco's native permission model (Consumer, Contributor, Collaborator, Coordinator).
  • Missing Authorities Must Not Crash Bulk Ingestion: In legacy systems, orphaned users or decommissioned Active Directory groups frequently linger on documents. If sent directly to Alfresco, the REST API rejects the entire payload with HTTP 400 Bad Request or 404 Not Found.

The oc-alfresco-output-connector was built from the ground up to address each of these challenges with enterprise precision.

2. Migration Mode Fast-Path: Zero Compute Overhead

Operating strictly under opencrawling.pipeline.mode=migration (or per-job pipelineMode: migration), the connector completely bypasses the resource-intensive AI vectorization pipeline:

Pipeline Stage RAG Mode (Default) Alfresco Migration Mode
Apache Tika Text Extraction Executed in isolated child JVMs Bypassed completely (0 CPU cycles)
Auto-Narrativization Copilot Mustache template rendering Bypassed completely
Token Chunking & Splitting TokenTextSplitter execution Bypassed completely
AI Vector Embeddings Ollama / OpenAI / HuggingFace Bypassed completely
Payload Target Vector databases & search engines Alfresco Content Services REST API v1
🛡

Strict Fail-Fast Protection: Attempting to run a job targeting the Alfresco output connector in RAG mode is rejected immediately with HTTP 409 Conflict ("AlfrescoOutputConnector only supports MIGRATION mode"), protecting operators from accidental misconfigurations.

3. Hierarchical Path Preservation (cm:folder) & Conflict Handling

The connector features an intelligent path resolution engine that evaluates the relativePath or relative_path metadata emitted by repository connectors (e.g. FileSystem, FileNet, SharePoint):

  • HIERARCHICAL (Default): Progressively inspects each segment of a nested document path (such as MigratedContent/v1/Legal/2026/Contracts). It checks whether intermediate cm:folder nodes exist via /nodes/{parentId}/children and automatically provisions missing parent directories. Resolved node IDs are cached in memory to eliminate redundant REST lookups.
  • FLAT: Ingests all documents directly into the base target folder defined by targetParentNodeId (e.g. -root-) and targetPathPrefix.

Duplicate Conflict Resolution

When a node with the same name already exists in the target folder, the connector handles it according to conflictStrategy:

  • OVERWRITE (Default): Replaces the binary stream via PUT /nodes/{nodeId}/content and updates properties in-place. If versioning is enabled (cm:versionable aspect), Alfresco automatically increments the document version.
  • AUTO_RENAME: Generates a timestamp-disambiguated filename before creation to avoid naming collisions.
  • FAIL: Aborts the upload of the duplicate and logs an error in the migration ledger.

4. Zero-Trust Security & Pre-Flight Authority Auditing

One of the most innovative features of the new connector is the AlfrescoAuthorityValidator.

Built on Java 25 Structured Concurrency (StructuredTaskScope) and thread-safe caching, the validator audits user and group authorities against target Alfresco endpoints (/people/{id} and /groups/{id}) to guarantee that only valid principals are submitted in permission payloads.

Authority Validation Modes

  • IN_FLIGHT (Default): Validates authorities on the fly during document ingestion. Results are cached in a thread-safe ConcurrentHashMap so that repeated users/groups across millions of documents incur zero additional network round-trips.
  • PRE_FLIGHT: Executes a parallel pre-crawl audit across all distinct authorities using StructuredTaskScope before content ingestion begins.
  • BOTH: Combines pre-flight discovery with in-flight verification for dynamically discovered identities.
  • DISABLED: Directly submits ACEs without pre-validation.

Built-in Authorities & Role Mapping

Standard Alfresco system authorities are recognized natively without issuing REST calls: GROUP_EVERYONE, EVERYONE, GUEST, ROLE_ANONYMOUS, ROLE_AUTHENTICATED, ROLE_ADMINISTRATOR, ADMIN.

OIS permissions are mapped to Alfresco roles:

  • read → Consumer
  • write → Contributor / Editor
  • delete → Collaborator
  • admin / full_control → Coordinator

The Missing Authority Gap Ledger Report

When missingAuthorityAction=SKIP (default), missing authorities are omitted from the node's permissions so valid ACEs are successfully applied, and the gap is captured in an audit ledger. At the conclusion of the migration, a structured JSON gap report is exported:

5. Document Lifecycle Actions & Trashcan Tombstones

Open Ingestion Standard (OIS) document lifecycle actions are fully supported:

  • UPSERT: Streams binary from Claim Check storage, creates or updates cm:content, sets properties, and synchronizes permissions.
  • DELETE: Resolved via tombstoneAction:
    • MOVE_TO_TRASH (Default): Calls DELETE /nodes/{nodeId}?permanent=false. Moves the document to the Alfresco Trashcan, preserving audit trails and enabling administrative recovery.
    • PERMANENT_DELETE: Calls DELETE /nodes/{nodeId}?permanent=true to purge the document permanently.

6. Lightweight Search Engine Tuning: noindex by Default

In high-throughput bulk migrations, indexing every document into Apache Solr simultaneously introduces substantial I/O overhead and memory contention. Furthermore, all migration writes and folder lookups execute directly against Alfresco's relational database (PostgreSQL)—meaning no search queries are required during ingestion.

In the decoupled Compose stack (docker-compose-decoupled-with-alfresco.yml):

  • Alfresco ACS defaults to -Dindex.subsystem.name=noindex.
  • Eliminates UnknownHostException: solr6 connection retries and log spam.
  • Reduces Alfresco container startup time from ~90s down to ~25–30s.
  • Saves ~2 GB RAM on the test/target host.
💡

Enabling Solr 6 on Demand: If full-text search indexing is needed on the target Alfresco instance, simply activate the preconfigured solr6 container using Docker Compose profiles:

export ALFRESCO_INDEX_SUBSYSTEM=solr6
docker compose -f oc-alfresco-output-connector/docker/docker-compose-decoupled-with-alfresco.yml --profile search up -d
