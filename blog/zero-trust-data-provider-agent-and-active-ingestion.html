01.The Multi-Agent System (MAS) Challenge

In modern enterprise architectures, Large Language Models (LLMs) and autonomous agent frameworks—such as Spring AI, LangGraph, AutoGen, CrewAI, and Antigravity—are deployed not as monolithic bots, but as collaborative swarms of specialized agents. An agent swarm tasked with preparing an audit package, resolving a regulatory compliance inquiry, or generating an investment briefing must access diverse enterprise content silos: Microsoft SharePoint, Alfresco, Hyland Content Innovation Cloud, IBM FileNet, OpenText Documentum, and Apache Ozone / AWS S3 data lakes.

However, traditional data ingestion architectures fail multi-agent swarms across three critical dimensions:

  1. The Context Security Leak: Standard agent tools expose vector databases via raw similarity search without passing caller identity. An agent querying the vector index risks surfacing restricted executive salary data or unredacted PII to unauthorized users.
  2. The Batch Latency Gap: Enterprise search traditionally relies on nightly or hourly batch indexing. When a business process concludes in Flowable or Alfresco Process Services (e.g., an urgent vendor contract approved 5 minutes ago), agents cannot access it until hours later.
  3. Passive vs. Active Ingestion: Traditional crawlers require human operators to statically pre-configure job boundaries. Autonomous agents facing dynamic goals need to lightweightly explore repository trees (dry-run discovery), formulate targeted crawl scopes on the fly, and initiate scoped ingestion pipelines with idempotency guarantees.
ⓘ

The Paradigm Shift: OpenCrawling bridges these gaps by becoming an active Data Provider Agent. Connected agents do not just query static vectors; they can inspect live repository hierarchies, evaluate pre-embedding governance, trigger real-time ingestions, and inspect lakehouse metadata sidecars—all bounded strictly to the caller's origin permissions.

02.The 4-Phase Active Ingestion Architecture

Under the architecture delivered in Issue #203, OpenCrawling provides an end-to-end active ingestion lifecycle:

Phase 1: Lightweight Discovery & Repository Exploration

Agents can inspect repository structures and metadata without triggering expensive full-scale downloads or vector embeddings. Using the new MCP exploration tools, agents retrieve folder trees, MIME types, and document counts across registered connectors (Alfresco, SharePoint, CMIS, Documentum, FileNet, M-Files, Hyland CIC, etc.).

Phase 2: Pre-Embedding Governance & Four-Eyes Approval

Before any extracted text is converted into high-dimensional vectors or committed to persistent data lakes, it passes through the in-flight Governance Gate (GovernanceGate). The gate evaluates PII redaction rules, tokenizes sensitive entities (SSN, IBAN, Credit Cards, Emails), and verifies whether the operation requires four-eyes administrative approval (requiresApproval).

Phase 3: Targeted On-Demand Ingestion

When an agent determines that specific documents or sub-folders must be indexed, it submits a targeted ingestion request via MCP or REST (POST /api/jobs/dynamic or POST /api/jobs/single-document). The job is dynamically orchestrated with custom token-chunking rules, deduplication idempotency keys, and source-level Access Control List (ACL) extraction.

Phase 4: Zero-Trust Identity-Aware Retrieval

When querying the vectorized knowledge base or inspecting persistent cloud migration sidecars (<key>.ois.json), OpenCrawling enforces Fail-Closed Zero-Trust evaluation. Deny rules authoritatively override grants, and callers are bound by OAuth 2.0 RFC 8693 delegated multi-agent identity.

04.In-Flight Pre-Embedding Governance: ALLOW, REDACT, DROP

A cornerstone of Luis Cabaceira's implementation is the in-flight Pre-Embedding Governance Gate (GovernanceGate) in oc-runtime. Unlike traditional search engines that index raw text and attempt post-hoc filtering, OpenCrawling intercepts documents before tokenization and vectorization: 

// Document processing pipeline with in-flight Governance Gate
public Mono<Void> process(IngestionMessage message) {
    return governanceGate.evaluate(message)
        .flatMap(decision -> switch (decision.action()) {
            case ALLOW  -> proceedToExtractionAndEmbedding(message);
            case REDACT -> {
                message.setText(decision.sanitizedText());
                message.addMetadata("ois:governance", decision.auditRecord());
                yield proceedToExtractionAndEmbedding(message);
            }
            case DROP   -> {
                log.warn("Document {} rejected by governance policy: {}", message.id(), decision.reason());
                yield publishTombstoneOrAuditTrace(message, decision);
            }
        });
}

The governance gate records immutable audit findings directly into the document's ois:governance metadata block:

  • decision: Normative OIS policy outcome (ALLOW, REDACT, DROP).
  • redactionCategories: Specific sensitive entity classes redacted (e.g., EMAIL, SSN, CREDIT_CARD, IBAN, PHONE).
  • policyId & evaluatedAt: ISO 8601 audit timestamp and policy rule identifier.
  • Cryptographic Tamper Protection: ois:governance and ois:provenance are registered in GovernanceGate.PROTECTED_KEYS, preventing downstream crawlers or transformation hooks from forging policy decisions.

06.Delegated Multi-Agent Identity (OAuth 2.0 RFC 8693)

When an autonomous agent acts on behalf of a human user, security cannot rely on service-account permissions. OpenCrawling enforces OAuth 2.0 Token Exchange (RFC 8693) delegation:

  • onBehalfOf (sub): The verified human user principal whose source permissions bound the entire ingestion and retrieval boundary.
  • actorAgent (act.sub): The SPIFFE ID or URI of the autonomous agent orchestrating the operation.
  • Normative Fail-Closed Enforcement: If an agent attempts to explore, ingest, or retrieve a document outside the human principal's permission tree, the request is authoritatively blocked with FAIL_CLOSED access denial.

07.Verified by Automated Conformance Testing

To ensure that the reference implementation and the Open Ingestion Standard (OIS) remain in lockstep, Issue #203 introduces the ois-conformance CI verification job.

On every pull request and commit to main, OpenCrawling downloads the live document.schema.json from the OIS specification repository and validates all emitted migration sidecars, tombstones, and governed envelopes using strict format assertions. If the spec and the implementation drift by even a single property, the build fails.

git clone https://github.com/opencrawling/opencrawling.git
cd opencrawling

# Launch the decoupled stack (PostgreSQL, Kafka, Redis, Ollama, oc-mcp-server)
docker compose -f docker-compose-decoupled.yml up -d

# Verify MCP Server handshake and run end-to-end integration tests
./scripts/test-mcp-decoupled.sh
