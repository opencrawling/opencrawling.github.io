Strict Public vs. Internal Isolation & Real Zammad 7.2 RAG: Announcing the Zammad Repository Connector

Support helpdesks hold some of an enterprise's richest operational knowledge—and some of its sharpest access-control hazards. Today we are releasing the native Zammad Helpdesk & Knowledge Base Repository Connector (oc-zammad-repository-connector, merged in PR #372), built on the official Zammad REST API v1, Java 25 Virtual Threads, strict public vs. internal article ACL separation, and end-to-end verified against a live Zammad 7.2.3 + Elasticsearch 9.5.5 stack.

1. Why Helpdesk RAG Breaks Without Article-Level Isolation

In an ITSM and helpdesk platform like Zammad, a single support ticket mixes two completely different trust zones: customer-facing replies (internal: false) and confidential internal agent triage notes, escalation runbooks, and diagnostic dumps (internal: true).

Flattening an entire ticket thread into one vector document—or indexing tickets without preserving Zammad's group, customer, and shared-organization boundaries—immediately leaks internal engineering notes to customers and exposes one customer's incidents to another organization. Even worse, Zammad Knowledge Base articles carry granular category role permissions and future-scheduled publication and archiving timestamps that naive scrapers routinely ignore.

✅

Verified Against Real Zammad 7.2.3 + Elasticsearch 9.5.5: Every API call, incremental Elasticsearch delta query, Knowledge Base permission lookup, binary attachment stream, tombstone deletion, and 5-persona MCP Zero-Trust scenario is automatically verified in CI against official ghcr.io/zammad/zammad:7.2.3-0008 and elasticsearch:9.5.5 containers.

2. Architecture & Decoupled Ingestion Flow

ZammadRepositoryConnector connects to self-hosted or Zammad Cloud instances over REST API v1 (/api/v1/...) using personal HTTP access tokens (Authorization: Token token=…), OAuth2 Bearer tokens, or Basic authentication, with optional X-On-Behalf-Of user delegation. Tickets are processed concurrently on Java 25 Virtual Threads via StructuredTaskScope and bounded semaphores, streaming binary attachments through size-capped temporary files (TempFileInputStream) into OpenCrawling's Claim-Check Store and Kafka pipeline.

3. Strict Public vs. Internal Ticket & Attachment Partitioning

Instead of merging public replies and private agent notes into a single document, the connector partitions every ticket according to article-granularity:

  • SPLIT_PUBLIC_AND_INTERNAL (default): Emits one OIS HTML document for customer-visible articles (zammad://<host>/tickets/<id>/public) and a separate OIS document for internal agent notes (zammad://<host>/tickets/<id>/internal). If a ticket contains only internal notes, no empty /public document is emitted—preventing ticket titles, tags, and owner metadata from leaking to customers.
  • PER_ARTICLE: Emits one OIS document per article (zammad://<host>/tickets/<id>/articles/<articleId>) for fine-grained citation and attribution.
  • PUBLIC_ONLY: Ingests only customer-visible articles and their attachments.
  • Binary Attachment Streaming & Deduplication: Streams real attachments via GET /api/v1/ticket_attachment/{ticket}/{article}/{att} (default cap 50 MiB), skips Zammad's synthetic content-alternative: true email HTML duplicates, and strictly inherits the parent article's public or internal ACL.

4. Fail-Closed Zero-Trust ACL Mapping

ZammadSecurityMapper translates Zammad's native authorization model into OIS SecurityConfig rules enforced authoritatively by the Secure MCP Server (DocumentAccessGate / McpAclEvaluator):

Mapping between Zammad entities and Open Ingestion Standard (OIS) security principals
Zammad Entity OIS Security Principals Guarantee
Public Ticket Thread & Public Attachments group:zammad-group-<group>, user:<customerEmail>, and group:zammad-org-<org> (only if organization.shared == true) Non-shared organizations (shared: false) never grant cross-colleague read access.
Internal Agent Notes & Internal Attachments group:zammad-group-<group> only Customer and organization principals—plus zammad.customer and zammad.organization metadata—are stripped.
Knowledge Base Answers group:zammad-role-<role> from Zammad's computed permissions_effective (or public only when published & allow-public-kb=true) Categories whose explicit granular permissions deny all roles (access: "none") fail closed instead of falling back to all agent groups.
Unresolvable / Orphan Group Empty SecurityConfig (permissions: []) Strict fail-closed behavior—never defaults to public.

5. Hardened Against Real Zammad 7.2 API Behavior

Running our connector against a live Zammad 7.2.3-0008 + Elasticsearch 9.5.5 deployment surfaced several real-world API details that we hardened directly into the v1 release:

  • Knowledge Base REST Contract: Loads KB structure via POST /api/v1/knowledge_bases/init (with automatic GET fallback on 404/405), fetches translation bodies with explicit comma-joined ?include_contents=<content_ids>, resolves KnowledgeBaseLocale.system_locale_id against Locale assets, and reads authoritative permissions_effective.
  • Scheduled Publishing (CanBePublished): Evaluates published_at, internal_at, and archived_at against Zammad's server clock—so drafts scheduled for next week are never prematurely indexed, and active answers scheduled for future archival remain searchable until their archive timestamp arrives.
  • Server-Clock Watermarks & Elasticsearch Range Syntax: Incremental SEARCH_DELTA queries use Lucene range syntax updated_at:[<watermark> TO *] anchored to Zammad's HTTP Date response header (minus a 60-second overlap) to resist host-vs-server clock skew.
  • Zammad Pagination Caps & Lifecycle Hygiene: Respects Zammad's hard endpoint limits (max 100 on /api/v1/tickets, max 200 on /api/v1/tickets/search), paginates metadata lookups (/groups, /roles, /ticket_states, /ticket_priorities), stops ticket paging only on empty or duplicate pages (preventing silent truncation or false FULL tombstones), closes owned HttpClient pools on disconnect(), refreshes user/organization caches on reconnect, and honors cooperative Flux cancellation without advancing state.
  • Pre-Crawl Discovery & On-Demand Fetch: Implements DiscoverableRepositoryConnector (explore, dryRun, crawlStart) and DocumentFetchingRepositoryConnector (fetchDocument) with page-by-page VisibilityFilter enforcement for AI agents.
